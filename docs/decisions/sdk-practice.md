# Release engineering and provider config: what three comparable SDKs actually do

Resolves wayfinder ticket 01 of `.scratch/providers-and-rigor/`.

Every claim below was read from the repository at the commit fetched on
2026-08-10, not from memory. Where a repository has no evidence for a practice,
this document says **absent** rather than inferring one.

## The three studied

| | Repo | Version studied | Why chosen |
| --- | --- | --- | --- |
| **T2S** | `Text2SqlAgent/text2sql-framework` | `pyproject` 0.4.0 | The owner's reference. Solo-maintainer, LangChain-optional. |

### One observed defect worth recording

SUP's `mark-release` job sets `body: ${{ needs.release-notes.outputs.release-body }}`,
but its `needs:` list is `[build, publish]` and the workflow defines no
`release-notes` job. The expression resolves empty; the release body comes from
`generateReleaseNotes: true` instead. Evidence that a hand-maintained release
workflow drifts even inside LangChain — an argument for generation over hand-editing.

## 2. The owner's question: multiple providers and their keys

Three genuinely different mechanisms. Ranked from most closed to most open.

### T2S — a closed `if`-ladder, keys never touched

`text2sql/agent.py`:

```python
def _get_backend(model_str: str) -> _Backend:
    """Parse 'provider:model_name' and return the matching native backend."""
    ...
    if provider == "anthropic":
        return _AnthropicBackend(model_name)
    if provider == "openai":
        return _OpenAIBackend(model_name)
    raise ValueError(
        f"Unsupported provider: {provider!r}. "
        "Native backends are 'anthropic' and 'openai'. For OpenAI-compatible "
        "endpoints (OpenRouter, Ollama, vLLM, ...), use 'openai:<model>' and set "
        "OPENAI_BASE_URL. ..."
    )
```

**Closed enum. Two providers, both hardcoded, no registration seam.** Keys are
never read by the framework — `anthropic.Anthropic()` and `openai.OpenAI()` are
constructed bare and pick up `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` from the
vendor SDK's own defaults. Config file: none. The escape hatch is explicitly a
protocol adapter, not an extension point: any OpenAI-compatible vendor is
reached as `openai:<model>` plus `OPENAI_BASE_URL`, which the code reads
directly (`base_url = os.environ.get("OPENAI_BASE_URL")`). A third provider
with its own wire protocol requires a fork.

### SUP — no mechanism at all, by design

`create_supervisor(model: LanguageModelLike, ...)`. The caller constructs the
chat model and passes the object. The library never sees a provider name, a
key, or an env var. **Maximally open and zero-cost, because the problem is
handed entirely to the caller** — which works for a library, and does not work
for anything with a UI or a config file, since there is nothing to configure.

### DA — an open registry *and* a user-editable config file, two layers

**Layer 1, the SDK — an open registry.** `deepagents/profiles/provider/provider_profiles.py`:

> "The registry is consumed by `resolve_model` and is the extension point for
> controlling `init_chat_model` kwargs, running pre-initialization side effects,
> and deriving kwargs from runtime state (e.g. environment variables)."

```python
register_provider_profile(
    "my_provider",
    ProviderProfile(init_kwargs={"temperature": 0.7}),
)
```

Keys are `"openai"` or a full `"openai:gpt-5.4"`. Built-ins (`nvidia`,
`openai`, `openrouter`) are registered lazily on first access through the same
call any third party uses — the definition of an open extension point.

**Layer 2, the app — a TOML file with an env-var *name*, never a secret.**
`~/.deepagents/config.toml`, `[models.providers.<name>]`, typed by
`ProviderConfig`:

```python
api_key_env: str
"""Name of the environment variable that holds the API key.

This is the env var *name* (e.g., `"OPENAI_API_KEY"`), not the secret
itself. The app resolves it at startup to verify credentials before model
creation.
"""
```

and, on `params`:

> "Do not set `api_key` here — the early credential check runs before `params`
> are read, so the app will reject the model before it sees the key. Use
> `api_key_env` to point at an environment variable instead."

The file also carries `base_url` / `base_url_env`, `models`, `enabled`,
`display_name`, `api_key_url` (for the auth UI's "get a key" link), and
`class_path` — a `module.path:ClassName` escape hatch that instantiates an
arbitrary `BaseChatModel` via importlib, with the trust model stated in the
docstring ("the same trust model as `pyproject.toml` build scripts"). A
completely unknown provider is therefore configurable **in a file, with no fork
and no code**. Env vars additionally support a `DEEPAGENTS_CODE_` prefix that
shadows the canonical name, with the empty-string case defined.

### Us — open at the model string, **closed at the credential**

`init_chat_model(...)` is called from six sites, so any provider LangChain
supports resolves from a model string today: that half is open and inherited.
Two of our own tables are closed:

- `_extras.PROVIDER_EXTRAS` — 5 prefixes. **Benign**: hint-only, and
  `provider_extra_hint` returns `None` for an unknown prefix rather than
  guessing. An unknown provider degrades to LangChain's own ImportError.
- `api/model_resolution.ACCEPTED_CREDENTIAL_KEYS` — **at the time this research
  was commissioned**, a `frozenset` of exactly `ANTHROPIC_API_KEY`,
  `OPENAI_API_KEY`, `OLLAMA_API_KEY`, `OLLAMA_HOST`. A key for any other
  provider posted from the editor was **silently dropped** by the
  `if name not in ACCEPTED_CREDENTIAL_KEYS: continue` branch, and
  `resolve_model`'s default chain was a three-branch `os.getenv` ladder.

**This closed half was fixed by ticket 02 while this document was being
written**, and the landed shape is the one recommended below: a new
`openstategraph/providers.py` declares `ProviderSpec`, a `ProviderCatalogue`, and
a `PROVIDERS_GROUP = "openstategraph.providers"` entry point, so a third party
registers a provider from their own distribution with no fork. `resolve_model`
now asks `provider_catalogue().default_spec()`, and the allow-list is *derived*
— `accepted_credential_keys()` returns `credential_env_vars()` from the live
catalogue, with `ACCEPTED_CREDENTIAL_KEYS` kept as an import-time snapshot for
back-compatibility while `apply_credentials` calls the function. The security
property (a request may never write an arbitrary env var) is preserved;
registering a provider is now what makes its key forwardable.

The four names above are the *pre-ticket-02* set and stay written as history.
The derived set is **five** for the built-ins today: Ollama's `env_vars` became
`("OLLAMA_API_KEY", "OLLAMA_HOST")` — it had declared `env_vars=()`, which made
it always configured on an *ambient* daemon credential — and `OPTIONAL_ENV_VARS`
now holds `OLLAMA_ENDPOINT` alone, since an endpoint with a working default can
never be what makes a provider usable. That is `credential_env_vars()`'s whole
job: what a request may write, which is a wider question than what makes a
provider configured.

What remains open from this comparison is DA's **second** layer: a versioned,
human- and agent-editable provider config *file* keyed on `api_key_env`. An
entry point requires publishing a distribution; a file does not. That is
ticket 03.

## 3. Recommendations, as deltas from what we already have

### Adopt now

1. **A provider config file whose key field is an env-var *name*.** Copy DA's
   `api_key_env` discipline verbatim, including the "this is the name, not the
   secret" docstring and the "do not put `api_key` in `params`" rule. It is the
   exact shape the map already demands ("secrets only ever in .env") and it is
   the only one of the three that has actually built it. *Reason: it makes the
   provider set open without ever putting a secret in a versioned file.* → ticket 03.

2. ~~**Turn `ACCEPTED_CREDENTIAL_KEYS` from a closed set into a derived one.**~~
   **Done — ticket 02 landed during this research.** Recorded because the
   reasoning still governs: keep the allow-list (refusing arbitrary writes into
   process-global `os.environ` is correct, and none of the three does better),
   but derive its membership from the registered providers' credential env-var
   names rather than a literal frozenset — the security property and the closed
   provider set had been the same line of code, and they are separate concerns.

3. **`concurrency: { group: ..., cancel-in-progress: true }` on `ci.yml`.**
   Both Lang* repos have it; we have none, so every push to a PR leaves the
   previous run burning a runner. One block, zero risk. *Reason: cheapest
   delta on this list.*

4. **Test the Python versions we advertise.** `requires-python = ">=3.11"` and
   classifiers claim 3.11/3.12/3.13; CI runs 3.12 only. SUP's comment states
   the principle we should copy — lint on one version, test on **min and max**.
   *Reason: a 3.11-incompatible syntax or a 3.13 stdlib removal ships today
   with a green build.*

5. ~~**`register_provider_profile`-shaped seam, not a subclass ladder.**~~
   **Also satisfied by ticket 02**, via `ProviderSpec` + the
   `openstategraph.providers` entry-point group. The corroborating evidence: DA's
   registry is a `dict[str, ProviderProfile]` of *declarative data* with
   `init_kwargs`, an `init_kwargs_factory` for env-derived values, and a
   documented merge order — no class per provider. That matches our own
   Registry-everywhere rule and our slot-table precedent. *Reason: it is the
   proven shape, and a provider class hierarchy would be inheritance that has
   not earned itself.* Keep `ProviderSpec` declarative for the same reason; if a
   provider ever needs env-derived kwargs, copy DA's `init_kwargs_factory`
   rather than adding a subclass.

### Adopt at 1.0

6. **PyPI Trusted Publishing (OIDC).** Both Lang* repos use
   `pypa/gh-action-pypi-publish` with `id-token: write` and no stored secret;
   we carry a long-lived `PYPI_API_TOKEN`. `release.yml` already names this as
   the preferred successor and the blocker as "the project must exist on PyPI
   under a real repository" — so this is scheduled, not overlooked. Do it in
   the same step that removes the `PLACEHOLDER` URLs. *Reason: removes the only
   long-lived credential in the repo.*

7. **Conventional-commit PR titles + release-please for the version bump and
   CHANGELOG.** Our CHANGELOG is genuinely better *prose* than DA's generated
   one, and hand-writing it is affordable at our commit rate — so this is a 1.0
   item, not a now item. What to take when we do: the `!`-in-the-**title** rule
   (release-please reads the squash commit, not the PR body — a trap worth
   knowing before we adopt), and the changelog-sections table that decides
   which commit types are user-visible. *Reason: the discipline scales; today
   the hand-written version is an asset, not a liability.*

8. **SHA-pin third-party actions.** DA pins every action to a SHA with a
   version comment; SUP and we use floating tags. *Reason: supply chain, and it
   only becomes urgent once we publish something worth attacking.*

9. **`dependabot.yml` and `CODEOWNERS`.** DA has both; we have neither.
   *Reason: both are review-load management, which we do not have yet.*

### Deliberately differ

10. **Keep `__version__` derived from `importlib.metadata`, not duplicated.**
    DA duplicates the version into `_version.py` and pays for it with a CI job,
    a pre-commit hook, a release-please `extra-files` entry, an
    `x-release-please-version` magic comment and a per-package unit test. T2S
    duplicates it and has **drifted**: `pyproject` 0.4.0, `__init__` 0.3.0.
    Our one line does the same job with none of the machinery. *Reason: the
    duplication only exists to serve release-please; do not import the problem
    along with the tool.* If we adopt release-please (7), keep the derived
    `__version__` and let it write only `pyproject.toml`.

11. **Keep the tag as the release trigger.** DA and SUP both release from
    `main` on a human action, tagging afterwards. Ours puts the decision in the
    artifact — the pre-release/TestPyPI choice is read off the tag shape, "so
    the decision lives in the thing being released rather than in whoever
    clicked the button" (`release.yml`). *Reason: the property is worth more
    than convention-matching, and DA's `RELEASING.md` has ~15 troubleshooting
    sections largely about reconciling tags with merged release PRs — a class
    of failure a tag trigger does not have.*

12. **Keep `docs-freshness` and `clean-install`.** No studied repo has a docs
    gate. On install proof: DA has TestPyPI + `pre-release-checks`, SUP has
    neither; our `clean_install_proof.sh` — install the built wheel into an
    empty venv **outside** the checkout with `PYTHONPATH` empty — tests
    something a TestPyPI upload does not. *Reason: these are ours and they are
    ahead; do not trade them for convention.*

13. **Keep the architecture checklist in the PR template.** DA's template
    optimizes for a high-volume external contributor funnel (title format, one
    package per PR, "large pasted AI descriptions may be ignored"). Ours
    optimizes for `CLAUDE.md` conformance. Different problems. *Reason: we do
    not have DA's contributor volume, and we do have DA's architectural
    surface.* Worth stealing from theirs when we open up: the "one package per
    PR" and "don't touch the lockfile" rules.

## 4. Where we are worse than all three

**One item, and it is the ticket's subject — now closed by ticket 02, recorded
here because the comparison is what justified the fix.** As commissioned,
`ACCEPTED_CREDENTIAL_KEYS` was a literal `frozenset` of four names and the
*only* credential path from the editor to a run. On the axis of "can a user
supply a key for a provider the authors did not enumerate":

- T2S never handles keys — the vendor SDK reads its own env var, so any key
  works for the two providers it supports, and nothing is dropped.
- SUP never sees a key at all — the caller built the model.
- DA lets a user *declare* an arbitrary provider's key variable in
  `config.toml` via `api_key_env`.
- **We silently discarded it.** Not "unsupported provider" — the loop's
  `continue` produced no warning and no entry in the returned `filled` list.

We were the only one of the four that could *drop a key it was handed*. With
ticket 02 landed we now sit between DA and the rest: a provider registered
through the `openstategraph.providers` entry point makes its key forwardable,
which is stronger than T2S and SUP, and weaker than DA only in that a
distribution must be published where DA accepts a config file (ticket 03).

Two secondary items, each worse than all three but already tracked:

- **`project.urls` is `PLACEHOLDER`.** All three ship real Homepage/Repository
  URLs. Known and gated (`backend/pyproject.toml` names the grep), but it is
  the one thing that would land visibly broken on a PyPI page.
- **No `concurrency` block.** T2S has no CI to compare, so strictly this is
  worse than the two that have CI, not all three.
